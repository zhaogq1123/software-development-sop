# S0 项目手册

## 目标

一份文件 `artifacts/_project/S0-01-项目手册.md`，让任何需求的 S1 开工时，10 分钟内知道：代码放哪、哪些仓不能随便改、公共机制怎么用、要做某类功能该参照哪个现成功能、构建环境长什么样。

它不是代码基线，不追求覆盖所有模块。只记「被用过两次以上、以后还会用」的事实。

## 什么时候做

| 时机 | 做什么 |
|------|--------|
| 首次 | 执行者自己做，不问用户：按模板建文件，**只填当前需求会碰到的仓和机制**（仓库地图可以全列，一行一个；其余章节按需），每条有出处；其他章节留「待回填」。「环境」章节由 S1 交付选项里用户所选形态和 S2 Step 0 的实测结果填。正确性靠后续需求走读时以代码为准逐条纠正，不要求用户通读 |
| S1 代码走读时 | 走读发现的稳定事实（公共工具类、配置表、登记机制）当场回填对应章节 |
| R 复盘时 | 「实现时才发现的事实」逐条回填；在「回填记录」加一行 |
| 环境变化时 | 「环境」章节更新基线 commit、依赖同步状态 |

## 规则

1. 每条事实带出处：`文件路径:行号` 或 `文件路径#方法名`。没有出处的不写。
2. 写「怎么用」，不写「有什么」。例：「发号用 `{Helper}#next(type)`，type 在 `{Type}` 枚举加一项，格式仿已有项」，而不是列出该类所有方法。
3. 发现手册与代码不符，以代码为准，改手册并在该行标日期。
4. 不写需求专属内容。某需求的字典编码、流程 key、模板编码属于该需求的 S2 产物；但它们**占用了什么**要登记到「登记占用」，供并行需求避让。
5. 「平台登记清单」是 S1 平台数据取样和上线前核对的依据：做一个功能通常要在哪些别的服务的库或配置里登记数据，漏了会怎样。第一次从已有需求的上线手册和配置导出里倒推，按本项目实际写，不照搬模板示例。
6. 「术语映射」记业务术语对应的代码字段或字典项（例：原文的「{业务类型}」对应 `{表}.{列}` 还是某字典的哪几项），出处到代码。S1 遇到新术语当场查清回填，不留到联调。
7. 手册超过 300 行时，把参照功能索引拆成独立文件，手册里留链接。

## 产出

`artifacts/_project/S0-01-项目手册.md`，结构见同目录 `S0-01-项目手册.模板.md`；`artifacts/_project/S0-02-precheck.json`（项目级：`api_prefixes` `table_prefixes` 覆盖全部仓，不只本需求；`fe_aliases`；`ref_dirs` 只读参照目录，用于跨服务路径与类核对；`identity_fields`；`project_terms` 供 SOP lint，见 SOP约束 › lint 查什么）。

## 出口

- 本需求 S1 要用的章节（至少：仓库地图、共享边界、相关公共机制、相关参照功能）已有内容且出处可打开。
- 「环境」章节的基线 commit 与构建环境当前分支一致（S2 Step 0 确认过）。
