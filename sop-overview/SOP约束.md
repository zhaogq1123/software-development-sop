# SOP 约束

本文约束 sop-v2 自身。执行需求时不用读；改任何 skill、模板、precheck 前必须读，改完跑：

```
python sop-s2-implement-deliver/precheck.py --lint-sop <sop-v2 目录> --config artifacts/_project/precheck.json
```

末行 `RESULT: PASS` 才算改完。

## 1. 只写通用流程

| 层 | 放什么 | 位置 | 换项目时 |
|----|--------|------|---------|
| skill | 步骤、出口、门禁、问题分类、模板骨架、precheck 检查逻辑 | `sop-v2/sop-*` | 不改 |
| 项目手册 | 仓库地图、共享边界、公共机制、术语映射、参照功能、平台登记、登记占用、环境 | `artifacts/_project/项目手册.md` | 重建一份 |
| precheck 参数 | 接口前缀、表前缀、前端别名、参考目录、身份字段、项目专有名词 | `artifacts/_project/precheck.json` | S0 建，S2 Step 0 补 |
| 需求产物 | 本需求的口径、编码、设计、坑 | `artifacts/{需求}/` | 不复用 |

- skill 里不出现任何项目或需求专有内容：仓名、服务名、包名、类名、表名、字段名、字典编码、配置键、地址、人名、需求编号、某个业务场景独有的规则。举例只用占位符：`{仓}`、`{Helper}`、`tb_{xxx}`。
- 技术栈细节（具体构建工具的参数、框架注解、命令）只出现在 precheck 专项检查和模板示例里，示例注明「以项目手册「环境」为准」；正文写意图（「测试是否被构建配置跳过」），不写某个工具的开关名。
- 某个需求踩到的坑，先问「换一个项目还会发生吗」：会 → 写成通用规则或 precheck 检查；不会 → 回填项目手册，不进 skill。

## 2. 篇幅上限

| 对象 | 上限 |
|------|------|
| 每个 `SKILL.md` | 120 行 |
| 其他 `.md`（总纲、模板） | 200 行 |
| 全部 `.md` 合计（不含 README） | 1120 行 |
| `precheck.py` | 1280 行 |

md 合计与 `precheck.py` 上限上调，是因为原文落盘、图清单、决定表到验收、改动面到文件写在 `precheck.py`，精简版补了评审摘要与交付选项。不另开文件。

超限 lint 即 FAIL。超了只能删或合并，不能拆新文件绕过。上限本身要改，同时改 `precheck.py` 的 `LINT_LIMITS` 并写明理由。

## 3. 增删规则

1. 加规则前依次试：做成 precheck 检查 → 做成模板里的字段或表头 → 并进已有规则。都不行才加一句话。
2. 新增必须对应一次真实问题（处理记录编号或复盘条目），写在变更说明里，不写进正文。
3. 一条规则只写一处，其他地方写「见 生命周期 › {标题}」。
4. 禁止补丁式写法：带日期的修订说明、「再次强调」「特别注意」、为某次事故单列的禁令、同一意思换说法重复。
5. 被 precheck 或模板吸收的规则，从正文删掉。
6. 清单（设计自查、决策类别、平台登记）按类别组织，超过一屏说明该拆成 precheck 检查或参照功能。

## 4. lint 查什么

`--lint-sop` 查三件事：篇幅上限（L1）；正文出现具体日期（L2）；出现 `precheck.json` 里 `project_terms` 的任一项（L3，大小写不敏感）。`project_terms` 由 S0 维护：仓短名、服务名、包名前缀、业务专有名词、有辨识度的接口与表前缀。
