# 可选加速项（不是前提）

**开箱即用不需要本文件。** 第一次用 sop-v2 直接从 S0 开始，执行者自己建手册首版，环境形态由用户在 S1 交付选项里选。本文件只列「做了能少一轮验证」的事，以及离线快照形态下刷新代码的做法。

## 让本机能编译

执行者在 S2 Step 0 自己补偿（离线模式、本地安装工作区内依赖、父构件桩）仍不能编译时会提示本项。在能编译的机器上用构建工具把依赖全部下载到本地缓存（后端依赖仓库、前端依赖目录、父构建文件），打包拷到本机对应位置，工具链主版本保持一致。具体命令写进项目手册「环境」。

拷过来后告诉执行者「依赖已同步」，它会实测一次离线编译，之后编译在本机就是硬门禁。

## 代码快照刷新

仅离线快照形态适用（本机能 `git fetch` 真实仓的，直接 rebase）。快照与真实仓没有共同历史，所以不 rebase，而是重导快照、重放 patch：

1. 你在真实仓所在机器把改动涉及的仓导出成当前代码（`git archive` 或直接打包目录），拷到本机。
2. 执行者把新代码导入为快照的新提交（覆盖对应子目录，提交信息写「快照 {日期}」）。
3. 执行者从新快照切 `feature/{需求编号}-r{N}`，按子目录 `git apply --3way` 重放上一轮的 patch，冲突就地解决、提交。
4. 重新跑 precheck，生成新 patch；项目手册「环境」更新快照日期。

什么时候需要：S2 Step 0 你回答「快照之后真实仓有新提交」，或软回退后全量仍因基线漂移失败。

## 用户侧软回退（与快照刷新分工）

真实仓已叠过多轮、状态说不清、或 apply 失败，但快照基线仍准：不要打远距增量。丢弃 `feature/{需求}` 上本需求改动（或新建分支），回到改动包 README 记载的基线，只打当前终包 `patches/` 全量（生命周期 › 当前位置选择表「其他」）。

软回退是用户侧动作；快照刷新是执行者侧重导。先软回退，仍失败再刷新。
