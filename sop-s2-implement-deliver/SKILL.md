# S2 实现与交付

## 目标

交付物到手即可编译、部署、按清单验证；已证明/未证明一眼可见。衡量：首次编译过；S3 r1 无 A/B，也无本该审查发现的 C。

## 输入

S1（改动面已确认）、项目手册、`artifacts/_project/S0-02-precheck.json`。

## 步骤

### 0. 环境核对

形态以 S1「交付选项」为准（生命周期 › 环境形态）；本步只实测，写入 `S2-01`。不符则停下由用户改选。手册「环境」未过期的直接用，只补缺：

- 工具链；按形态实测编译/部署入口；各改动目录的仓根、子路径、最近提交、远程。
- **编译不通先补偿**：离线模式；工作区内依赖先本地安装；缺父构件造最小桩（仅本机，不进交付）。仍不通再停下，写清卡在哪。
- 单测能力：构建是否跳过测试、有无框架、测试文件数 →「有 / 无（原因）」。
- 离线快照问一句：快照日后真实仓有无新提交？有则先「环境准备 › 代码快照刷新」。首次顺带问开发/发布线/生产 tag 规则，记入手册。
- `precheck.json` 项目级：缺项从**全部仓**补前缀，不只本需求。

### 1. 开分支

新功能/小改动：`feature/{需求编号}`。线上缺陷：从生产 tag 切 `hotfix/{编号}`。在线仓每仓一个；大仓快照只切一个。记下基线 commit。

### 2. 写代码

- 按改动面逐行；参照怎么写就怎么写。要动未列文件：先补改动面并说明。无 git 先 `git init`。调他模块成员前打开源码核对（有源码必核；仅 jar 则对已有调用或反编译）；受检异常按同模块先例。不可编译时尤其不能猜（自我纠错）。
- 设计标「需要单测」的纯逻辑：抽成不依赖缓存/远程/库的方法。能力「有」→写单测随交付；「无」→不擅自改构建（共享边界）；边界用例进验证清单，单测门禁「无法证明」。
- 设计错缺：直接改并标 `[S2 修订 日期]`；涉口径/调用者/数据范围/状态前置→待定，必问未关不交付相关代码。
- 要动共享仓而 S1 未写：停该项→待定。常量/错误码/字典进常量类；前端枚举走字典翻译。

### 3. 本地提交

`git add -A && git commit -m "{需求编号}: ..."`。未提交不交付。

### 4. SQL、配置、上线手册

- **SQL**：可重入（验证循环；Q3）；固定 id/号段；头写检查/回滚与「适用：最终态|升级清理」。`reset_test.sql` 仅测试。
- **配置** `S2-03-config/*.diff`：文件、锚点、执行前搜索；标最终态或升级清理；回滚自包含（产出模板）。
- **上线手册**：十类写**当前最终态 0→1**；首次只含最终态；升级清理进「三附」。可贴原文或 sha256（Q1）。共享包「合入后构建发布」。登记引取样或「上线前核对」。每节「人工动作：需要/无」；「无法证明」进「风险」。

### 5. 验证清单与 verify

从 AC 展开，加编译/单测/部署/上线前核对。执行列：执行者 / verify / 手工。r1：编译+单测+部署+verify+≤8 手工冒烟。

可接口验证的 AC → `S2-04-verify/`（产出模板）；读 `env.local`（不入库，只交 `env.example`）。鉴权不清读网关写入手册「环境」；走不通标「手工」。自造桩结果=自测，不进 `S2/`。仅后端且选了选项 → `S2-05-api/`：OpenAPI（调用者/状态前置/数据范围/错误码原文/AC）+ Postman（覆盖 verify 全部 AC，每接口至少一反例）。期望来自 AC。A1 核路径与覆盖。

### 6. 静态检查与编译

```
python <本 skill 目录>/precheck.py --out S2 --repo <目录> [--repo ...] --base <目录名>=<基线> --config artifacts/_project/S0-02-precheck.json \
       [--no-patch | --handoff handoff/{需求}-r{N} --write-manifest]
```

`--out`→`S2/`（S1 同级）；分支/PR 加 `--no-patch`，改动包给 `--handoff`。改动面每个要改仓都要 `--repo`（含已 init）；每个 patch 也须有对应 `--repo`。「不改」须写「不改：原因」。末行 `RESULT: PASS`；WARN 只解释与本次相关；S1（安全）类进审查「后续优化」。纯配置仍跑；无代码改动不按空包失败。

**终检**：patches/README/manifest 齐后再对同一 `--handoff` 跑；门禁「precheck」只认这次。先跑再塞未检 patch 不算过。能编译则编译；单测「有」则跑且运行数>0。不通过不交付。

### 7. 独立审查

**新上下文**做；输入仅：`S1-02`、`S1-01`、设计、`S1-03`、本次 diff（无实现过程、无纠错说明）。产出 `S2-08`（产出模板）：

- **AC 映射**：每条 `文件:行` + 结论（已实现/未实现/本期不做 D-xx/环境登记+手册节）。已实现所引行必须是该 AC 实现。拆 AC 规则见「交付选项」。verify 在测的不能是本期不做（R1）。「平台承载」须落到手册登记步骤或判未实现。
- **管控**：审批/状态前置/数据范围/次数时效逐入口核；未生效→需求不符。
- **设计漂移**：走读接触点 vs 设计 vs 实现；不一致补 `[S2 修订]` 或改码。
- **问题**：按问题分类。需求不符/交付与部署→回 Step 2 修并重跑 Step 6；安全/实现质量→「后续优化」。

审查文件只由审查者写；执行者只改问题表「状态」+修复位置。需求不符修完由新上下文复核 AC。重跑 precheck（R1）。

### 8. 交付物与门禁表

出包前自我纠错；改码重跑 Step 6；触及已审查实现或需求不符→Step 7 复核。交付说明须有门禁表（含**交付可用性**）。按「交付可用性」找茬通过才勾 A；有 `S3-02` 写 B（S2 首包可进 S3 时补 r1）。

- 在线仓：推分支、建 PR；`S2/` 即交付物。
- 离线/不可编译：只维护当前终包（白名单：README/manifest/precheck-report/`patches/`全量/至多相邻增量；见产出模板）。禁嵌套 `S2/`。无历史编年。出 r{N+1} 前把 r{N} 移入 `_archived`。

### 9. 更新当前位置

仅交付可用性已通过。按「S3 固定版式」写「你要做的」；只问一问时用「S2 有一个问题」。写入 `00-当前位置`，对话最后一条原样发用户。

## 规则

- 做不了的事进清单由能做的人做，门禁「无法证明」，不写「本地核对通过」。
- S3 带回的可静态查出的编译错→加 precheck + selftest。
- S2 出口不需用户评审；不写执行记录；不交未提交文件。门禁失败自修到过再交付（决策）。

## 产出

`artifacts/{需求}/S2/`：`S2-01`…`S2-08`（按选项可有 `S2-05-api/`）；不可编译另有 `handoff/{需求}-r{N}/`。

## 出口

- 分支有提交，`git status` 干净。
- precheck `RESULT: PASS`；可编译形态编译过。
- `S2-08` 无需求不符/交付与部署「待修」。
- 门禁表每项有结果与依据（含交付可用性）；「无法证明」已进手册「风险」。
