# S2 实现与交付

## 目标

交付物拿到手不需要再问问题就能编译、部署、按清单验证；哪些已证明、哪些没证明一眼看得出。衡量：首次编译通过；S3 r1 没有 A/B 类问题，也没有本该被审查发现的 C 类问题。

## 输入

S1 产出（评审通过）、项目手册、`artifacts/_project/S0-02-precheck.json`。

## 步骤

### 0. 环境核对

环境形态以用户在 S1「交付选项」里的选择为准（生命周期 › 环境形态），本步只实测核对，写进 `S2/S2-01-环境探测.md`；实测与所选不符时停下说明（例：选了可编译但补偿后仍编译不过），由用户改选，执行者不自行改判。项目手册「环境」已有且未过期的直接用，只补缺项：

- 工具链版本；按所选形态实测：可编译的跑一次编译命令（命令以项目手册「环境」为准），可部署的确认部署入口与账号可用；代码形态核对每个改动目录的仓根与子路径、最近提交、远程地址。
- **编译不通时先补偿再报告**：构建工具离线模式；工作区内已有源码的依赖模块先本地安装；缺失的父构件造最小桩（只为本机编译，不进交付）。仍不通再按上面停下说明，写明卡在哪个依赖。
- 测试基础设施：构建配置是否跳过测试、有无测试框架依赖、测试目录下文件数。写成「单测能力：有 / 无（原因）」。- 离线快照形态问用户一句：「这些目录在真实仓从 {快照日期} 之后有没有新提交？」有则先按「环境准备 › 代码快照刷新」。第一次顺带问开发分支、发布线分支、生产版本 tag 规则，记进项目手册。
- `precheck.json` 是**项目级**的：缺项时从全部仓归纳接口前缀、表前缀补上，不只写本需求的。

### 1. 开分支

新功能、小改动：从开发分支切 `feature/{需求编号}`。线上缺陷：从生产版本对应的 tag/分支切 `hotfix/{编号}`。在线仓每仓一个；大仓快照只切一个。记下基线 commit。

### 2. 写代码

- 按 S1「改动面」逐行做，参照功能怎么写就怎么写；改动面没有的仓或文件要动，先补进改动面并说明。无 git 的目录先 `git init` 建基线提交再改。
- 设计说明标为「需要单测」的纯逻辑（时效与窗口、状态迁移、权限判定、金额/编号计算），抽成不依赖缓存、远程调用、数据库的方法，入参出参都是普通值。
- 单测能力「有」：为这些方法写单测，随代码交付。能力「无」：不擅自改构建配置或流水线（按共享边界处理）；这些逻辑的边界在验证清单里各写一条用例，门禁表单测记「无法证明（原因）」。
- 实现中发现设计说明有错或缺：直接改，标 `[S2 修订 日期]`；涉及业务口径、调用者、数据范围、状态前置的进待定决策，必问项关闭前相关代码不交付。
- 发现要动共享仓而 S1 没写：停该项，进待定决策。
- 常量、错误码、字典编码集中在常量类/枚举；前端枚举展示走字典翻译。

### 3. 本地提交

`git add -A && git commit -m "{需求编号}: ..."`。未提交不交付。

### 4. SQL、配置、上线手册

- **SQL 可重复执行**（生命周期 › 验证循环；precheck Q3 检查）。应用生成主键的表写固定 id 并说明号段。每个文件头写执行前检查和回滚。测试环境需要复位的另附 `S2-02-sql/reset_test.sql`。
- **配置改动** `S2-03-config/*.diff`：写清配置文件、锚点，执行前先搜索是否已存在。
- **上线手册**从 S1「上线清单草稿」展开，十类全写（见产出模板），没有的写「无」。SQL、配置贴原文，SQL 也可写文件名 + sha256 引用（precheck Q1 比对）。共享依赖包写「合入发布线后由构建发布」。登记值引用 S1 取样表的行；未取样的写成「上线前核对」。每节标「人工动作：需要 / 无」。门禁表里「无法证明」的项写进「风险」。

### 5. 验证清单与 verify

从 `AC-xx` 展开，加上编译、单测、部署、上线前核对。每条标执行方式：执行者 / verify / 手工。r1 范围：编译 + 单测 + 部署 + verify + ≤ 8 条手工冒烟。

能用接口调用验证的 AC 写进 `S2/S2-04-verify/`（模板见产出模板），读 `S2-04-verify/env.local` 的地址和账号，输出每条 `PASS/FAIL AC-xx`。`env.local` 不入库，只提交 `env.example`。鉴权方式不清楚的读网关或登录入口写进项目手册「环境」；走不通的标「手工」。只能对着自造桩跑的结果是自测，不算验证，输出不放在 `S2/`（生命周期 › 门禁与证据）。仅后端且选了对应交付选项：按最终代码写 `S2/S2-05-api/`（模板见产出模板）。接口文档是 OpenAPI 3，每个接口写调用者、状态前置、数据范围、错误码与原文文案、对应 AC；冒烟集合是 Postman Collection v2.1，覆盖 verify 的全部 AC，每个接口至少一条反例（状态不对、非本人数据、超次数）。期望值来自 AC。precheck A1 核对路径与 AC 覆盖。

### 6. 静态检查与编译

```
python <本 skill 目录>/precheck.py --out S2 --repo <目录> [--repo ...] --base <目录名>=<基线> --config artifacts/_project/S0-02-precheck.json \
       [--no-patch | --handoff handoff/{需求}-r{N} --write-manifest]
```

`--out` 指向 `S2/`（S1 取同级 `S1/`）；分支/PR 形态加 `--no-patch`，改动包形态给 `--handoff`。`--repo` 给改动面里每一个要改的仓（含无 git、已 `git init` 的）；handoff 里每个 patch 也必须有对应 `--repo`。改动面「不改」只能写「不改：原因」，叙述里写「无改动」不算豁免。末行必须 `RESULT: PASS`；WARN 在交付说明里只解释与本次改动相关的，S1（安全）类 WARN 记入审查「后续优化」。纯配置、数据变更仍跑本步，SQL 可重入不因类型跳过；没有代码改动时不按空包失败。

**终检**：handoff 的 patches / README / manifest 全部就位后，对同一 `--handoff` 再跑一次；门禁表「precheck」行只认这次报告。先跑 precheck 再往包里塞未检查的 patch，不算通过。

能编译的形态接着编译；单测能力「有」的跑单测，并确认报告里运行数大于 0。不通过不交付。

### 7. 独立审查

由**新上下文**（新会话或子代理）做，输入只给 `S1-02-需求与验收.md`、`S1-01-决定表.md`、设计说明、`S1-03-代码走读.md`、本次 diff，不给实现过程。产出 `S2/S2-08-审查.md`（模板见产出模板）：

- AC 实现映射：每条 AC 写实现位置 `文件:行` 和结论（已实现 / 未实现 / 本期不做 D-xx / 环境登记 + 上线手册节）。已实现所引的那一行必须就是该 AC 的实现，邻近行不算。环境登记写上线手册里真实存在的节名。仅前端或仅后端时按「生命周期 › 按需求类型裁剪 › 交付选项」拆 AC，本端部分照常判，不整条标本期不做（precheck R1：verify 在测的 AC 不能是本期不做）。「平台承载」不是结论：要么指出上线手册里的登记步骤，要么判未实现。
- 需求规定的管控（审批、状态前置、数据范围、次数与时效）逐个入口核对，没生效的记「需求不符」。
- 设计漂移：代码走读接触点（仿哪个参照、改哪个仓）与设计说明对照实现，不一致处补 `[S2 修订]` 或修代码。
- 问题按 生命周期 › 问题分类 登记。需求不符、交付与部署 → 回到 Step 2 修，重跑 Step 6；安全、实现质量 → 状态「后续优化」。

`S2-08-审查.md` 只由审查者写；执行者修完只改问题表「状态」列并附修复位置，不改结论和引用。修需求不符类后由新上下文复核对应 AC。重跑 precheck，R1 检查审查完整（每条 AC 有映射、结论用规定词、引用位置存在、阻塞类无「待修」）。

### 8. 交付物与门禁表

交付说明（PR 描述或改动包 README）必须有门禁表：编译、单测、precheck、审查、验证清单，每项写结果和依据（见产出模板）。

- 在线仓：推分支、建 PR。`S2/` 即交付物。
- 离线快照 / 不能编译：`handoff/{需求}-r{N}/`，每个改动目录一个 patch（`git format-patch <基线>..HEAD --relative=<子目录>`）。改动包只放 patch、README、manifest、precheck 报告；`S2/` 连同拷贝。r{N} 目录生成后不改，要改出 r{N+1}。

### 9. 更新当前位置：交付完成用生命周期 › 当前位置的「S3 待执行」；停下来只问一个问题时用「S2 有一个问题」。写进 `00-当前位置.md`，对话最后一条原样发给用户。

## 规则

- 做不了的事（部署、手工用例、本机不能跑的单测）写进验证清单由能做的人做，门禁表记「无法证明」，不写「本地核对通过」。
- S3 带回的每类编译错误，能静态查出的都加进 precheck，并在 `--selftest` 加用例。
- S2 出口不需要用户评审；不写执行记录、完成标准对照；不交付未提交的工作区文件。门禁失败自己修到通过再交付，不把修复动作列成用户待办（生命周期 › 决策）。

## 产出

`artifacts/{需求}/S2/`：`S2-01-环境探测.md`、`S2-02-sql/`、`S2-03-config/`、`S2-04-verify/`、`S2-06-上线手册.md`、`S2-07-验证清单.md`、`S2-08-审查.md`，按交付选项另有 `S2-05-api/`；不能编译形态另有 `handoff/{需求}-r{N}/`。

## 出口

- 分支有提交，`git status` 干净。
- precheck 末行 `RESULT: PASS`（纯配置/数据变更除外）；能编译形态编译通过。
- `S2-08-审查.md` 无需求不符、交付与部署类「待修」。
- 门禁表每项有结果和依据，「无法证明」的已写进上线手册「风险」。
