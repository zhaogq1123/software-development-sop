# S2 产出模板

所有形态都有 `S2/`：`S2-01-环境探测.md`、`S2-02-sql/`、`S2-03-config/`（配置中心改动，diff 形式）、`S2-04-verify/`、`S2-06-上线手册.md`、`S2-07-验证清单.md`。
在线仓的交付物是分支/PR；离线快照或不能编译的形态另有改动包。

## 改动包目录（离线快照 / 本机不可编译）

```
handoff/{需求编号}-r{N}/
  README.md
  manifest.txt
  precheck-report.txt
  patches/{目录名}.patch           相对基线的全量（每改动仓一个，--relative）
  {目录名}-r{K}to-r{N}.patch       可选；已应用到 rK 时用的增量（放本轮目录）
```

SQL、配置、手册、清单、verify 不复制，拷贝时连同 `S2/` 一起拷。更早轮次目录首页标「已废弃，勿用」。

### README.md

```
需求：{编号} {短名}      改动包：r{N}      生成日期：
快照日期 / 基线：{目录名} {commit} …
本轮范围：验证清单 第 {x} 节
与上一轮差异（r1 不写）：修了 r{N-1} 的 B-01…（给执行者）

## 用户本轮要做（与 00-当前位置「你要做的」同文；版式见生命周期 › 当前位置）
你要做的（目录：handoff/{需求}-r{N}/）

先选一行（只做这一行的代码；多仓多列）：
| 你当前已应用到 | {仓A} | {仓B} |
| 从未打过 / 仅基线 | 本包 patches/ 全量 | 本包 patches/ 全量 |
| 已到 rK | {仓A}-rKto-rN.patch | 无需再打 / {仓B}-rKto-rN.patch |
| 已到 rN | 代码都不用再打 | 代码都不用再打 |

再按序做（每步有「做」和「粘回」）：
1. SQL/配置/登记：{本轮改过的文件} — 粘回：检查与执行结果
2. 打 patch：只打上表你那一行 — 粘回：apply 输出
3. 编译 {模块} — 粘回：成功或错误末尾
4. 重启 {服务} + 复验 {行为} — 粘回：请求/响应或说明
5. 前端：构建部署 → 刷新或重登 → 复验 — 粘回：现象
6. 验证清单本轮行 / 冒烟 — 粘回：每条通过或失败

仍待你回报：… / 无

## 门禁
| 门禁 | 结果 | 依据 |
| 编译 | 无法证明（本机不能编译，请在下方执行） | |
| 单测 | 通过 n 条 / 无法证明（原因） | |
| precheck | PASS | precheck-report.txt |
| 审查 | 需求不符 0 / 交付与部署 0；后续优化 n 条 | S2/S2-08-审查.md |
| 验证清单 | 本轮范围 | |

## 在真实仓里执行（每个目录，复制即可）
1. cd {真实仓根}; git checkout {开发分支或生产 tag}; git pull
   git checkout -b feature/{需求编号}
   git apply --3way --check patches/{目录名}.patch && git apply --3way patches/{目录名}.patch
   git add -A && git commit -m "{需求编号}: r{N}"
2. 编译 / 单测：{命令}
3. 按「用户本轮要做」与验证清单本轮行部署、执行，结果粘回
4. 全部通过后：git push，建 PR 到 {发布线分支}

apply 失败：把输出原样带回（A 类），不要手工改代码。
```

## S2-02-sql/*.sql（文件头）

```sql
-- 需求：{编号}   库：{库名}   执行顺序：{n}
-- 可重复执行：是
-- 执行前检查（输出现状，首次为 0、重跑为已存在，都可继续）：
--   SELECT COUNT(*) FROM information_schema.TABLES WHERE TABLE_SCHEMA = DATABASE() AND TABLE_NAME = 'tb_xxx';
-- 回滚：
--   DROP TABLE IF EXISTS tb_xxx;  /  DELETE FROM tb_dict WHERE type = '{类型}' AND code IN (...);

CREATE TABLE IF NOT EXISTS tb_xxx ( ... );

INSERT INTO tb_dict (id, type, code, name)
SELECT {固定id}, '{类型}', '{编码}', '{名称}' FROM DUAL
WHERE NOT EXISTS (SELECT 1 FROM tb_dict WHERE type = '{类型}' AND code = '{编码}');
```

`S2-02-sql/reset_test.sql`（可选，只用于测试环境，不进上线手册）：把本需求写入的数据和表清掉，回到部署前状态。

## S2-04-verify/

```
S2-04-verify/
  run.ps1         一条命令；Linux 下另附 run.sh
  cases.json      [{ "ac": "AC-01", "method": "POST", "path": "...", "body": {...}, "expect": { "code": "200", "jsonPath": "data.status", "equals": "1" } }]
  env.example     BASE_URL= / LOGIN_PATH= / USERNAME= / PASSWORD=   （复制成 env.local 填写；env.local 不入库）
  out.txt         执行输出
```

`run.ps1` 做四件事：读 `env.local` → 调登录接口取令牌 → 逐条按 `cases.json` 发请求、按 `jsonPath` 取值与 `equals` 比较 → 每条输出 `PASS AC-xx` 或 `FAIL AC-xx 期望 … 实际 …`（异常也记 FAIL）并写入 `out.txt`。登录接口、令牌字段、请求头名按项目手册「环境 › verify 鉴权」写。用例期望值来自 AC，不来自实现。

```

| # | 节 | 条目 | 操作 / 命令 | 期望 | 执行 | 本轮 |
| 1.1 | 编译 | | {项目手册「环境」的编译命令} | 构建成功 | 执行者或环境 | r1 |
| 1.2 | 单测 | | {单测命令} | 运行数 > 0 且全部通过；无测试能力则删本行 | 同上 | r1 |
| 2.1 | 数据 | S2-02-sql/xxx.sql | 先跑文件头检查 → 执行 | 执行无报错；重跑也无报错 | 环境 | r1 |
| 2.2 | 配置 | S2-03-config/xxx.diff | 按锚点改，已存在则跳过 | 重启无报错 | 环境 | r1 |
| 2.3 | 上线前核对 | 登记项 | {查询} | {期望值} | 环境 | r1 |
| 3.1 | verify | S2-04-verify/run.ps1 | 一条命令 | out.txt 无 FAIL | 环境 | r1 |
| 3.2 | 冒烟集合 | S2-05-api/冒烟.postman_collection.json（有则写） | 工具导入运行或 newman | 断言全部通过 | 环境 | r1 |
| 4.x | 冒烟 | AC-xx（含纯逻辑边界） | | | 手工 | r1 |
| 5.x | 全量 | AC-xx | | | 手工 | r2 |
| 6.x | 回归 | 已有功能 | | | 手工 | r2 |
```

「执行」列：执行者 / verify / 手工。「本轮」列：r1 / r2 / 重跑（引用上轮编号）/ 不跑。

要带回的信息（粘贴到对话即可）：apply 结果；编译与单测输出末尾；`S2-04-verify/out.txt`；手工条目每条 通过/失败（失败贴请求、响应、日志行）；实际部署 commit、实际用到的编码/配置。

## S2-06-上线手册.md

```
# 上线手册 — {需求}
最后更新：      范围：      代码：{分支} @ {commit}

每节标「人工动作：需要 / 无」。

## 风险（门禁表中「无法证明」的项及其补偿验证）
## 一、服务与发布顺序（共享依赖包：合入发布线后由构建发布）
## 二、数据库（每段：执行前检查 → SQL 原文 → 回滚；均可重复执行。或写「执行 S2-02-sql/{文件} sha256:{值}」代替原文）
## 三、配置中心（diff 原文、锚点、效果、已有功能影响、回滚）
## 四、定时任务
## 五、消息与缓存（运行时自动生成的标「无需人工配置或干预」）
## 六、页面、菜单与授权
## 七、外部登记（引用 S1 取样表；未取样的写「上线前核对：查询 + 期望」）
## 八、上线步骤
## 九、上线后验证与观察期（每类一条；看哪个日志关键字或页面、观察多久、出现什么就回滚）
## 十、回滚（倒序；已产生数据怎么处置；hotfix 写「同步回开发分支」）
```

## S2-08-审查.md（独立上下文产出；标题名 precheck R1 依赖，不改）

```
最后更新：      审查输入：需求与验收 / 决定表 / 设计说明 / 代码走读 / diff {基线}..{commit}

## AC 实现映射
| AC | 实现位置（文件:行） | 结论 |
| AC-01 | {仓}/src/.../XxxService.java:120 | 已实现 / 未实现 / 本期不做（D-xx） / 环境登记（上线手册第几节） |

## 管控核对（需求规定的审批、状态前置、数据范围、次数与时效）
| 管控（D/AC） | 入口 | 是否生效（文件:行） |

## 设计漂移
| 设计说明位置 | 实际实现 | 处理（补 [S2 修订] / 改代码） |

## 问题
| 编号 | 类别 | 问题 | 位置（文件:行） | 状态 |
| P-01 | 需求不符 / 交付与部署 / 安全 / 实现质量 | | | 待修 / 已修 / 后续优化 / 用户接受（日期） |
```

类别与处理见 生命周期 › 问题分类。结论只用上面四个词开头（precheck R1 检查），「平台承载」「环境侧」之类写成「环境登记」并指向上线手册，或判「未实现」。需求不符、交付与部署只能是「已修」或「用户接受」才能交付；「后续优化」的条目在 R 阶段交给用户排期。
