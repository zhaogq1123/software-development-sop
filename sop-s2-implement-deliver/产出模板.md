# S2 产出模板

所有形态都有 `S2/`：`S2-01-环境探测.md`、`S2-02-sql/`、`S2-03-config/`（配置中心改动，diff 形式）、`S2-04-verify/`、`S2-06-上线手册.md`、`S2-07-验证清单.md`。
在线仓的交付物是分支/PR；离线快照或不能编译的形态另有改动包。

## 改动包目录（离线快照 / 本机不可编译）

```
handoff/
  {需求编号}-r{N}/                 当前终包（用户只看这个；白名单如下，多一个都不行）
    README.md
    manifest.txt
    precheck-report.txt
    patches/{目录名}.patch              相对基线全量（必有）
    {目录名}-r{N-1}to-r{N}.patch        可选；仅相邻（任意轮次）；无 diff 或本轮 A 类则不生成
  _archived/{需求编号}/
    r{K}/                               更早终包（出 r{N} 时移入；勿用）
```

白名单硬规则：终包内**禁止** `S2/`、远距 `rKto-rN`（K&lt;N-1）、根目录其它文件/目录。`artifacts/{需求}/S2/` 与终包**并列**交付，不嵌套。出 r{N+1} 时把 r{N} 移入 `_archived`。「你要做的」只指当前终包。出包前快照基线 `git apply --check` 全量；有相邻增量则先落到上一轮终态再 check，结果树=交付 HEAD（README「基线自证」）。

### README.md

只含下列块（历史在 `_archived`/`S3-02`）。**内容预算**（超则未交付；H6）：≤80 行；差异≤5 短项；除 r{N}/r{N-1} 外不罗列更早轮号；欠账最多追一轮；WARN 只引报告条数；细节指 `artifacts/.../S2/`。

```
需求：{编号} {短名}      改动包：r{N}      生成日期：
快照日期 / 基线：{目录名} {commit} …
本轮范围：验证清单 第 {x} 节
与上一轮差异（r1 不写）：- B-01 …（≤5 条）
基线自证：全量 --check PASS；相邻增量链 = HEAD {commit}（无增量写「本轮仅全量」）

## 用户本轮要做（与 00-当前位置同文；版式见生命周期 › 当前位置）
你要做的（目录：handoff/{需求}-r{N}/）
先选一行（多仓多列）：
| 你当前已应用到 | {仓A} | {仓B} |
| 从未打过 / 仅基线 | 本包 patches/ 全量 | 本包 patches/ 全量 |
| 正好已到 r{N-1}（未手工改） | {仓A}-r{N-1}to-r{N}.patch | 无需再打 |
| 其他（含已到 rN） | 已到 rN：不用再打；否则丢弃本需求改动→基线→全量 | 同左 |
前置（一次性；无则删节）：
1. 打上表所选 → 编译 {模块} → 重启 {服务}（为何重启）— 粘回：…
2. 配置：`S2-03-config/{完整文件名}`（用途：…）— 粘回：是否已配
本轮操作（在哪做/点什么/预期/粘回；引用须全路径+用途，禁止「02」「04」）：
1. 页面操作：… — 预期：… — 粘回：…
2. SQL：`S2-02-sql/{完整文件名}`（用途：…）检查后重跑 — 粘回：…
3. 前端部署→刷新或重登→复验（写清验什么）— 粘回：…
4. 冒烟 {条目名} — 粘回：每条通过或失败
仍待你回报（同样写全名+用途+粘回；禁止「之后继续：02、04」）：无 / …

## 门禁
| 门禁 | 结果 | 依据 |
| 编译 | 无法证明（本机不能编译，请在下方执行） | |
| 单测 | 通过 n 条 / 无法证明（原因） | |
| precheck | PASS | precheck-report.txt |
| 审查 | 需求不符 0 / 交付与部署 0；后续优化 n 条 | S2/S2-08-审查.md |
| 交付可用性 | 通过 | 找茬 1–7 无否（生命周期 › 交付可用性） |
| 验证清单 | 本轮范围 | |

## 在真实仓里执行（每个目录，复制即可）
1. cd {真实仓根}; git checkout {开发分支或生产 tag}; git pull
   git checkout -b feature/{需求编号}
   git apply --3way --check patches/{目录名}.patch && git apply --3way patches/{目录名}.patch
   git add -A && git commit -m "{需求编号}: r{N}"
2. 编译 / 单测：{命令}
3. 按「用户本轮要做」与验证清单本轮行部署、执行，结果粘回
4. 全部通过后：git push，建 PR 到 {发布线分支}

apply 失败：原样带回（A 类），不要手工改；先按选择表「其他」软回退打全量，仍失败再快照刷新。
```

## S2-02-sql/*.sql（文件头）

文件头只写**当前约束**（可重入、检查、回滚），禁止事故编年。标 `适用：最终态`（新环境主路径）或 `适用：升级清理`（仅已有旧库/旧包环境；不进上线手册首次步骤）。

```sql
-- 需求：{编号}   库：{库名}   执行顺序：{n}   适用：最终态|升级清理
-- 可重复执行：是
-- 执行前检查（输出现状，首次为 0、重跑为已存在，都可继续）：
--   SELECT COUNT(*) FROM information_schema.TABLES WHERE TABLE_SCHEMA = DATABASE() AND TABLE_NAME = 'tb_xxx';
-- 回滚：
--   DROP TABLE IF EXISTS tb_xxx;  /  DELETE FROM tb_dict WHERE type = '{类型}' AND code IN (...);

CREATE TABLE IF NOT EXISTS tb_xxx ( ... );

INSERT INTO tb_dict (id, type, code, name)
SELECT {固定id}, '{类型}', '{编码}', '{名称}' FROM DUAL
WHERE NOT EXISTS (SELECT 1 FROM tb_dict WHERE type = '{类型}' AND code = '{编码}');
```

`S2-02-sql/reset_test.sql`（可选，只用于测试环境，不进上线手册）：把本需求写入的数据和表清掉，回到部署前状态。

## S2-03-config/*.diff

```
# 适用：最终态 | 升级清理
# 配置文件：{dataId 或文件名}   位置：{锚点，例：xxx.whitelist 列表末尾}
# 执行前检查：搜索 {键}，已存在则跳过（删除类：不存在则跳过）
# 回滚：必须自包含（写明加回/恢复步骤）；禁止「按旧 handoff 包内已删文件」
+   - /{前缀}/{新路径}/**
```

**最终态**=新环境目标配置（首次必做只列这类）。**升级清理**=删错配/仅迁移需要；可名含 `rollback`/`cleanup`，只进手册「三附」，不作 0→1 必做。

## S2-04-verify/

```
S2-04-verify/
```

```
最后更新：

| # | 节 | 条目 | 操作 / 命令 | 期望 | 执行 | 本轮 |
| 1.1 | 编译 | | {项目手册「环境」的编译命令} | 构建成功 | 执行者或环境 | r1 |
| 1.2 | 单测 | | {单测命令} | 运行数 > 0 且全部通过；无测试能力则删本行 | 同上 | r1 |
| 2.1 | 数据 | S2-02-sql/xxx.sql | 先跑文件头检查 → 执行 | 执行无报错；重跑也无报错 | 环境 | r1 |
| 2.2 | 配置 | S2-03-config/xxx.diff | 按锚点改，已存在则跳过 | 重启无报错 | 环境 | r1 |
| 2.3 | 上线前核对 | 登记项 | {查询} | {期望值} | 环境 | r1 |
| 3.1 | verify | S2-04-verify/run.ps1 | 一条命令 | out.txt 无 FAIL | 环境 | r1 |
| 3.2 | 冒烟集合 | S2-05-api/冒烟.postman_collection.json（有则写） | 工具导入运行或 newman | 断言全部通过 | 环境 | r1 |
| 4.x | 冒烟 | AC-xx（含纯逻辑边界） | | | 手工 | r1 |
| 5.x | 全量 | AC-xx | | | 手工 | r2 |
| 6.x | 回归 | 已有功能 | | | 手工 | r2 |
```

「执行」：执行者/verify/手工。「本轮」：r1/r2/重跑/不跑。带回：apply、编译单测末尾、`out.txt`、手工通过/失败、实际 commit 与编码配置。

## S2-06-上线手册.md

```
# 上线手册 — {需求}
最后更新：  范围：  代码：{分支} @{commit}
每节「人工动作：需要/无」。**0→1 最终态**：不写事故编年；过时口径整节改写。
## 风险（「无法证明」及补偿）
## 一、服务与发布顺序（共享包：合入后构建发布）
## 二、数据库（仅最终态脚本；检查→原文/sha256→回滚）
## 三、配置中心（仅最终期望；锚点/效果/自包含回滚）
## 三附、升级清理（可选；ALTER/rollback；新环境跳过）
## 四、定时任务
## 五、消息与缓存
## 六、页面、菜单与授权
## 七、外部登记（S1 取样或「上线前核对」）
## 八、上线步骤（首次路径不点名升级清理文件）
## 九、上线后验证与观察期
## 十、回滚（倒序；hotfix「同步回开发分支」）
```

## S2-08-审查.md（独立上下文产出；标题名 precheck R1 依赖，不改）

```
最后更新：      审查输入：需求与验收 / 决定表 / 设计说明 / 代码走读 / diff {基线}..{commit}

## AC 实现映射
| AC | 实现位置（文件:行） | 结论 |
| AC-01 | {仓}/src/.../XxxService.java:120 | 已实现 / 未实现 / 本期不做（D-xx） / 环境登记（上线手册第几节） |

## 管控核对（需求规定的审批、状态前置、数据范围、次数与时效）
| 管控（D/AC） | 入口 | 是否生效（文件:行） |

## 设计漂移
| 设计说明位置 | 实际实现 | 处理（补 [S2 修订] / 改代码） |

## 问题
| 编号 | 类别 | 问题 | 位置（文件:行） | 状态 |
| P-01 | 需求不符 / 交付与部署 / 安全 / 实现质量 | | | 待修 / 已修 / 后续优化 / 用户接受（日期） |
```

类别与处理见 生命周期 › 问题分类。结论只用上面四个词开头（precheck R1 检查），「平台承载」「环境侧」之类写成「环境登记」并指向上线手册，或判「未实现」。需求不符、交付与部署只能是「已修」或「用户接受」才能交付；「后续优化」的条目在 R 阶段交给用户排期。
