# S3 验证与修复

## 目标

每一轮之后，下一轮必须比上一轮更接近「全部通过」。同一问题不出现在两轮结果里。

## 输入

本轮交付物、`S2/S2-07-验证清单.md`、本轮结果（执行者自己跑出的 + 带回的，格式不限）。

## 步骤

### 1. 执行与归档

清单里标「执行者」的自己跑；「verify」「手工」的由执行人做，结果带回。全部结果原样存为 `S3/S3-01-结果-r{N}.md`。在 `S3/S3-02-处理记录.md` 加一节 r{N}，逐条编号（A-01、B-01、C-01、D-01…）。信息不够分类的先按能判断的处理，缺的写进下一轮清单「请补充」。

r1 带回了编译、单测结果的，回填 S2 门禁表（「无法证明」改为实际结果）。

### 2. 按类分流

**A 基线**（patch 应用失败）：不改代码、不造远距增量。在线仓：rebase。离线：先让用户按选择表「其他」软回退打本包全量（环境准备 › 用户侧软回退）；仍失败再快照刷新。下一包只出全量。项目手册「环境」更新基线。

**B 编译 / 单测**：逐条修。每条问一句「能不能静态查出来」，能就加进 precheck 并补 `--selftest` 用例（新检查项编号写进处理记录）。同类错误算一条。修完一类、出下一包前：对本轮改过的文件再对照工作区源码与同模块先例扫一遍同类用法，不带着刚修过的同类问题出下一包。

**C 行为**：先按「生命周期 › 问题分类」定类别（安全、实现质量类记入 `S2/S2-08-审查.md`「后续优化」，不阻塞本轮）；再判断实现错还是设计错，在处理记录「判断」列写一句理由（引用 AC、D 编号或代码位置）。实现错 → 修代码。设计错 → 先改设计说明（标 `[S3 修订 日期]`），口径变化的进待定决策，再修代码。用户看到归因不对可以推翻，不需要逐条确认。信息不够不猜，下一轮清单加「请补充 X」。同一条连续两轮没过，停下来重读参照实现或问用户，不再改第三版碰运气。

**D 环境事实**：实际值与设计值不同（编码被占用、配置项不同、流程 key 改了）→ 回写 S2 的 sql / config / 手册 / 代码常量，并更新项目手册「登记占用」。影响口径的进待定决策。

### 3. 待定决策一次问

本轮新增的 `Q-xx` 按「生命周期 › 决策」分级，攒齐一次发给用户。必问项未关闭时涉及的代码不进下一轮交付；其余修复不阻塞。

### 4. 交付下一轮

按 S2 步骤 3–9 交付 r{N+1}（改了需求不符类问题的，重做 Step 7 审查对应 AC）。先把现行 `handoff/{需求}-r{N}/` 移入 `_archived/{需求}/r{N}/`，再生成新终包（增量策略见生命周期 › 当前位置与产出模板）。交付说明「与上一轮差异」逐条引用本轮编号。清单本轮列只标：上轮失败重跑 + 受改动影响 + 尚未执行。

`00-当前位置.md`、对话最后一条、改动包 README「用户本轮要做」三处同文，必须用生命周期 › 当前位置「S3 固定版式」：选一行表 → 前置 → 本轮操作 → 仍待你回报；每步有粘回；引用写全路径+用途（禁止「02/04」缩写、禁止「之后按清单继续」一笔带过）。缺表、缺粘回、缩写指代、本轮改过的 sql/config/登记未入步骤 = 未交付完。数据被污染时先跑 `S2-02-sql/reset_test.sql`。

### 5. 收口

最新结果每条「通过」时：上线手册「代码」行写最终 commit；门禁表改实际结果；在线仓建 PR（生命周期 › 合并与发包）；离线快照出最终改动包。「你要做的」改「待合并」。处理记录里「实现时才发现的事实」留给 R。

## 规则

- 结果原文不改，结论写在处理记录。未执行就标未执行，不用「本地核对」代替。

## 产出

`S3/S3-01-结果-r{N}.md`、`S3/S3-02-处理记录.md`、下一轮交付物。

## 出口

最新结果验证清单 100% 通过；门禁表无「失败」；在线仓 PR 已建，离线快照最终改动包已交付。未收口前每一轮的「你要做的」符合生命周期 › 当前位置对 S3 的要求。
