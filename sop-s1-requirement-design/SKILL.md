# S1 需求与设计

## 目标

一次性把「做什么、照谁做、依赖哪些平台数据、哪些要人定」写清，使 S2 开工后不再回头问设计问题。

## 输入

需求原文（md、txt、docx、doc、pdf）先经 `sop-s2-implement-deliver/precheck.py --ingest` 落成 `S1/原文/正文.md`。正文是 UTF-8 文件，不经过控制台；图在 `media/`，清单里仍是待看、无法看，或空节旁被标成忽略的，S1 不能出口。决定表只引用该文件和清单里已读的图。另有 `artifacts/_project/项目手册.md`、代码。

## 步骤

### 0. 判断类型

按「生命周期 › 按需求类型裁剪」判断类型，写进 `当前位置.md`。小改动、线上缺陷、纯配置数据只写一个 `S1/设计.md`（结构见产出模板「精简版」），下面步骤按需做；新功能做全部步骤。

线上缺陷先复现再分析：拿到现象、请求、日志、数据，在代码里定位到 `文件:行`，写清根因再写修法。复现不了的，写明缺什么信息，进待定决策。

### 1. 决定表

读 `S1/原文/正文.md`，把每条有行为含义的句子登记成 `D-xx`：原句、来源（原文位置或图）、状态。原文互相矛盾的两条都登记，矛盾进待定决策。原句是证据，只记一次，别处引编号。

原文没写的**业务行为**是待定决策（必问），不是设计空间；原文没写的**技术细节**照参照功能做（照先例），不打扰用户。

### 2. 需求与验收

把 `D-xx` 归并成 `REQ-xx`，每条带 `AC-xx`。AC 必须是在环境里能操作、能看到结果的句子，粒度要能区分相近参数（例：重发间隔和有效期各一条 AC）。写不出 AC 的 REQ 说明口径不清，进待定决策。

### 3. 参照代码走读

从项目手册「参照功能索引」找现成功能，顺着它读完整条链：入口 → 业务层 → 持久层 → 调用的其他服务 → 配置 → 权限登记。每个接触点记文件、方法、本需求仿/改/新建。

准备复用的接口**读到实现**，确认入参语义和限制；读完能不能用写进「不可用接口登记」。要碰的共享仓列出已有调用方。手册里没有合适参照时用 grep 找最像的，读完加进手册。走读完按接触点给出「交付选项」建议值（生命周期 › 按需求类型裁剪），写进待定决策。

### 4. 平台登记数据取样

代码只证明机制，实例数据在别的服务的库或配置中心里。按项目手册「平台登记清单」中本需求涉及的项：

- 能取到就取：本地有配置导出、库脚本、或用户顺手贴来的数据，记下参照功能那一行原样、本需求要加的行、编码占用（查手册「登记占用」并登记本需求的占用）。
- 取不到的不阻塞：在上线清单草稿里写成「上线前核对：{查询语句或检查方法}，期望 {值}」，由环境执行人在部署时核对。
- 只有影响设计本身的（例如不确定该机制在本项目是否存在）才进待定决策。

### 5. 设计说明

只写 S2 开工必需的：接口契约、表、状态机、缓存键与时效、错误码与文案、改动面、共享边界触碰、上线清单草稿。深度以「S2 照着能直接写代码」为准，不留「方案级、S2 定稿」：

- 表的每个字段、接口的每个出参能追到 `AC-xx` 或 `D-xx`；追不到的不建。
- 接口写清调用者、数据范围、状态前置（例：哪个状态、谁的数据才能看）——这些是需求规定的管控，S2 审查按它判「需求不符」。
- 原文里的业务术语由执行者用代码证据定到字段或字典项：已有功能的页面标签、筛选键、字典、接口字段怎么用这个词。证据一致就写进项目手册「术语映射」并附出处；证据冲突或找不到才进必问。代码不留「待联调核对」之类标记（precheck T1）。
- 改动面每行到仓和文件（或路由、菜单等代码内登记），从代码走读「接触点」里标改/新建的行得出，不从 diff 倒推；它就是 S2 的任务清单，precheck C1/C2 按它核对。

交互流程选项开启时另写 `S1/交互流程.md`（模板见产出模板），箭头上的接口与接口契约同名。

写完过一遍模板里的「设计自查」（按类别，每类写一句怎么处理的；是提醒清单，不是门禁）。

### 6. 待定决策，一次问齐

按「生命周期 › 决策」分级。必问项给**建议值**、影响范围和「按建议会怎样」；照先例项写明参照了哪个功能。全部列在一份清单里一次发给用户：「逐条确认」类排在最前、要求逐条回复；其余必问可以一句「全按建议」关闭，也可以推翻任何一条。

用户回复后：新增 `D-xx`（来源写答复日期），`Q-xx` 状态改「已定 → D-xx」。必问项没有回复的保持待定，本阶段不出口。

### 7. 评审

先发设计说明开头的「评审摘要」（一屏）和待定决策，详细内容供查阅，请求一句话结论：「评审通过」或列修改项。改完再发一次。小改动和纯配置数据可以和待定决策合并成一次回复。

## 规则

- 不编造：原文、代码、参照功能里都没有的行为不写进设计，写进待定决策。
- 不改共享仓是建议值，不是禁令：要改就按「生命周期 › 共享边界」走。
- 不在 S1 写代码，但必须读代码。没「读到实现」的接口不允许出现在设计的「复用」位置。
- 不写 PRD、用户故事；时序图只写进可选的 `交互流程.md`；接口文档和冒烟集合按交付选项在 S2 产出。

## 产出

新功能：`artifacts/{需求}/S1/` 下 `决定表.md`、`需求与验收.md`、`代码走读.md`、`设计说明.md`、`待定决策.md`；可选 `交互流程.md`。
其他类型：`S1/设计.md`。结构见 `产出模板.md`。

## 出口

- 必问级 `Q-xx` 无「待定」行，每条关闭都引用用户回复日期；逐条确认类每条有单独回复；交付选项每行有用户选择（precheck D1）。
- 用户回复「评审通过」（记录日期）。
- 代码走读里每个「复用」接口「读到实现：是」；涉及的平台登记项有取样或有「上线前核对」。
- 改动面每行到仓和文件；设计用到的业务术语在项目手册「术语映射」里有对应字段。
- 项目手册「参照功能索引」「已知不可用接口」「登记占用」「术语映射」已回填。
